## Output Contract（必須）

記事案・構成案・本文案を出すときは、以下を必ず含める。

1. 想定読者（1行）＋**ペルソナ2〜3**（各: 呼び名／知りたいメイン／着地の求め／この記事で充足する不足）。**source.md・記事案・構成案では必須**（正本は「読者最優先」）。想定読者1行と Frontmatter の `target` は**ペルソナの要約**であり、別軸の読者像を立てない。公開本文・初稿本文へのペルソナ表の転載はしない（`target` 1行で足りる）
2. 検索意図（How-to / 比較 / チェックリスト）
3. 主キーワードと副キーワード
4. 記事の結論（3〜5点）
5. 構成案（H2中心、最大5前後）
6. 収益導線案
   - アフィリエイト導線
   - 広告配慮方針
   - デジタル商品CTA案
7. 内部リンク候補（既存・未公開の区別つき）
8. 免責文（執筆時点/仕様変更可能性）

任意（さらに良い）: 各ペルソナ向けの**サブ情報 +α**案（合否対象外。詳細は「読者最優先」）

## 文体・トーン

敬体ベースは維持する。問題は敬体か常体かではなく、**文末と段落の均質さ**（AI臭の正体）である。次の6ルールに従う。

1. **敬体ベース＋文末の多様化**
   - です・ます基調、平易な日本語（中学生〜社会人の初心者が読めるレベル）
   - 同一文末（〜です／〜ます）の連続を避け、文末をばらすのは**執筆時の望ましい工夫**。**L1の必須合否にはしない**（任意改善のみ。詳細は改善施策ノート §4.3.1）。記事末の**免責**は対象外
   - **です／ます切断（リズム目的の短い常体挿入）を必須としない**。切断のためだけの短文（「断定は避ける。」「読める範囲はここまで。」等）で執筆メタや意味重複を増やすのは、読者最優先に反する。意味のある山場に限る
   - **体言止め**は段落の**途中**の山場に限って使う（段落末では使わない）。ある程度の長さがある記事では**ゼロ回避**（少なくとも1回、段落途中で満たす）。**文比率の目標は設けない**（45〜75%／60%±5% 等は不採用）
   - 短い常体の断定は山場のみ混在可（例: 「特別な仕掛けはなし。」）。**段落の最後の文は敬体**（導入段落を含む。`です`／`ます`／`ください` 系）。常体や体言止めで段落を閉じない
   - 常体は意味の山場に使う（段落末は敬体のまま）。です／ます連打の切れ目として使うのは任意で、必須ではない
   - 一文の長さを意図的にばらす（短→長→短の拍）
2. **一人称は必要時だけ＋実在感要件**
   - 通常は主語を省略し、**「筆者」も連発しない**。「筆者」は実測・失敗談・確認範囲・未検証の境界を示す必要がある文だけに使う
   - 「筆者」を使う場合、同じ文か段落で使用理由（実測した／失敗した／確認範囲を限定する等）が読者に伝わるようにする
   - 「私」「当サイト」は使わない
   - 記事ごとに最低1つ、内部チェック用の根拠マーカーを置く（優先: **実測数値＋取得日**／**使用環境**／**失敗談**。無ければ次行の根拠バー）
   - 「一次情報」「筆者の確認範囲」は内部の判定語。公開見出しには原則出さず、「実際に試して分かったこと」「試した環境と結果」など読者の関心に合わせる
   - 実測を持たないテーマは捏造せず、確認範囲・参照元・未検証範囲を具体的に書く。**暦日（`YYYY-MM-DD`／`○年○月○日`）を本文の各節に連打する必要はない**（下記「暦日の置き方」）
   - **根拠バー（評価フェーズ）**: 薄味禁止。次のいずれかを本文で辿れること — **実測／一次ログ**、または **調査・公式ドキュメント・二次分析・SERP/GSC根拠**（Vault `toolarc.jp_評価フェーズ移行_現状と方針検討_2026-07-31` §5.2 と整合）
3. **断定と逡巡の使い分け**
   - 実測で確定したことは言い切る。未確定は「今回の環境では」「執筆時点で確認した範囲では」など、主語を増やさず範囲を限定する。暦日が必要なときは下記「暦日の置き方」
   - **結論の先延ばしは禁止**。「今日の結論」は維持する
4. **LLM空句の禁止** — 正本は [`llm-forbidden-phrases.md`](./llm-forbidden-phrases.md)。「最後に」「まさに」「体言止め」は禁止しない
5. **段落設計**
   - 1段落1トピック＋密度波形（密な段落2〜3個ごとに疎を1つ）
   - 「状況→理由→対策」の同一テンプレ連打を避ける
6. **因果に機構を一文添える** — 結果だけでなく、なぜそうなるかの仕組みを一文入れる

口語的なつなぎは可。「正直」「実際に」は使ってよいが、冗長な感嘆は避ける。英語用語は初出で日本語を添える（例: token（トークン））。推測は「〜と考えられる」「〜の可能性」と書く。

### 句読点

- 文末が丸括弧で終わる場合は `（…）` で閉じ、`（…）。` と句点を重ねない
- 括弧の後にも本文が続く場合は、文全体の終わりに通常どおり句点を置く
- 引用の閉じ `」` の直後に句点を置かない。本文を `」。` で検索し、当たったらその `。` を外す。`」` の直後から次の文を続ける（括弧の `（…）。` と同じ）
- Web記事では、鉤括弧の中を `です。` で閉じる小説・会話体（`「…です。」`）は使わない
- 引用が文末になる場合は `「…」` で閉じ、`「…」。` と句点を重ねない（上記と同じ）
- **括弧の入れ子は基本的に使わない**。`（「…」）` / `「（…）」` / `「(…)`」 のように括弧同士を重ねない。括弧内で語を目立たせたいときは鉤括弧を重ねず、`"…"` や `` `…` `` を使う。言い換えが楽なら文を分ける／「たとえば」でつなぐ。未公開リンクは `「準備中」`。`「（準備中）」` は避ける
- **`――` / 同型の `——` は使わない**（文中の間・見出し・`title`）。文中の〔状況〕――〔問い／ラベル〕は句点分割／読者への問い／「そのあと」等へ。見出し・タイトルの区切りは `｜`（または `：`）へ（正本: [`llm-forbidden-phrases.md`](./llm-forbidden-phrases.md)）。本文箇条の短い区切り `—`（単独）は別判断

## 記事の型

### 推奨構成

1. 導入（読者の悩みに共感、1〜3段落）
2. **今日の結論**（`> **今日の結論**` または `> **この記事の結論**` の引用ブロック、箇条書き 3〜5 点）
3. 本論（H2 単位で問題→原因→対策）
4. チェックリスト or 表（あるとよい）
5. まとめ / 次に読む
6. 免責（仕様変更・執筆時点の注記。**見出しにしない**。形式は「仕様・免責」節）

### 記事タイプ別の推奨導線

| タイプ         | 推奨導線                                                              |
| -------------- | --------------------------------------------------------------------- |
| How-to         | 手順・チェックリストで無料価値 → 記事末にデジタル商品 CTA             |
| 比較・選定     | 比較表 + 向く人/向かない人 → アフィリエイト（判断材料をリンク前後に） |
| チェックリスト | 本文で完結する価値 → テーマに合う CTA を1本に絞る                     |
| Hub            | スポークへの内部リンクを優先 → 必要に応じてシリーズ関連 CTA           |

### 見出し

- **H1 は記事タイトル1つのみ**（本文中に H1 を増やさない）
- **H2 は最大 5 前後**を目安（長文はシリーズ分割を優先。公開済み長文で超えることはある）
- H3 は H2 の下で論点を分けるときのみ
- 見出しだけを追っても「何が分かるか／何をするか」が推測できる情報量にする。「判断基準」「一次情報」「FAQ」など抽象ラベル単独は避ける
- 長文化させず、結論・対象・数字のいずれか1つを足す（例: 「判断基準」→「少人数なら先に埋める3つの軸」）
- 見出しにキーワードを無理に詰め込まない（自然な日本語優先）

### 箇条書き・表

- 箇条書きは **1項目 1〜2 行**、並列の粒度を揃える
- 比較・可否は **表** を優先（Markdown 表）
- 手順は番号付きリスト

### 読者最優先

検索着地の読者が今このページで何をしたいかを先に満たす。**L1合否の最優先軸**（改善施策ノート §4.3.1 項目13。他の必須項目・文体リズムより先に見る）。リンクの有無だけでは足りない。

#### ペルソナ充足（必須）

記事ごとに想定読者（ペルソナ）を**2〜3**用意する。**作成タイミングの正本は `source.md`（記事案・構成案）**。L1は source にあればそれを正とし、無ければ `target`・検索意図・今日の結論から立て直す。公開本文へのペルソナ一覧の掲載は不要。各ペルソナについて次を満たす。

- **知りたいこと**: その人が知りたいメイン情報は何か（1行で言える）
- **着地の求め**: どんな情報を求めてこの記事にたどり着いたか（検索語句・画面の困りごとに近い言葉）
- **不足の充足**: そのメインの不足情報が、この記事の約束の範囲内で本文に揃っているか。揃っていなければ要修正（source 時点では構成・結論案で賄えることを示す）。「この記事では扱わない」と境界を置いた範囲は充足義務の外（境界は書いてよい）

判定の芯: **想定したペルソナすべてについて、知りたいメイン情報が記事に記載されていること**（絶対）。source 欠落は L1 で補完判定するが、次の source 作成から必須とする。

#### 「今知りたいか／今クリックしたいか」フィルター（必須・L1最優先）

各段落・リスト・リンクを、次で見る。文体リズムより先に適用する。

- **今知りたいか**: その文がペルソナのメイン／着地の求めに対する**事実・手順・判断材料**か。執筆の実況・姿勢宣言・構成案内だけなら本論に置かない（削る／免責へ／事実の線引きに言い換える）
- **今クリックしたいか**: 内部リンクは、今の読者の次の一手として前後から動機が辿れるか（詳細は下記「内部リンク」）
- **境界の書き方**: 「断定しない」「本記事は判定しない」等の**姿勢の実況**は読者が知りたい本題ではない。必要な境界は**事実**で書く（例: 公式に保持日数が明記されていない）。記事全体の保証範囲は**免責**に書く
- **やってはいけない改善**: です／ます切断や合否回避のために、読者向けでない短い常体・メタ文言を増やすこと

#### サブ情報 +α（任意・さらに良い）

メインに加えて、知っておくと便利なサブ情報があるか。不足は任意改善として提示し、合否は落とさない。あると読者最優先として一段よくなる。

#### 内部リンク（必須・配置）

形式は `/blog/slug`。配置は次を満たす。冒頭リンクの一律禁止はしない。「扱わない」などの境界も書いてよい。

- **着地意図の完結**: title／今日の結論の約束は、他記事を開かずに満たす。結論の答えを「他記事へ行け」だけにしない。Hub／シリーズ入口は着地意図が地図なので、スポーク誘導をこの項の例外とする
- **リンクの動機**: 各内部リンクに「このリンクを今クリックしたいか」が前後の文から辿れること。動機がカニバル回避・シリーズ地図・担当分けの運営都合だけで、今の読者の次の一手になっていないなら、その位置には置かない（削除するか、本論・まとめへ移す）
- **用語の公開面**: 本文・見出し・`title` に編集室内語を出さない（例: 弱リンク、カニバル、Output Contract。見出しの「一次情報」「筆者の確認範囲」も避ける）。運用docsでは使ってよい
- **出口の場所**: 既定は、本論でその情報が必要になった箇所、またはまとめ／次に読む。導入・今日の結論への内部リンクは**禁止しない**。リンクを添えるかは、上記「今クリックしたいか」で決める

## Markdown ルール

- コードブロックに言語指定（`md`, `text`, `bash` など）
- 画像: `![説明](ファイル名.png)` — 説明文は具体的に（`captions.md` があればそれに合わせる）
- 内部リンク: `/blog/slug` 形式（slug は `lib/blog/posts.ts` のキー。未公開は「準備中」と書く）。**配置・動機は上記「読者最優先」の内部リンク**
- 水平線 `---` は大セクションの区切りに使う（乱用しない）
- 強調: 太字は**要点の語句のみ**（段落全体を太字にしない）
- CommonMark 制約: `**C#**は` / `**語（注）**は` のように、閉じ `**` の直前が `#`・全角括弧などの句読点だと太字が成立しない。表示は `MarkdownArticle` が自動補正する。新規原稿でも、インラインコードや括弧を太字の外へ出すと読みやすい（例: `` `C#` ``、`**Godot**（GDScript）`）

## Frontmatter（記事ドラフト用）

記事として出力するときは、先頭に YAML を付ける:

```yaml
---
title: "32文字前後で検索意図が分かるタイトル"
description: "120〜160文字（正本レンジ。完了前にUnicode実測）"
date: YYYY-MM-DD
tags:
  - タグ1
  - タグ2
site: toolarc.jp
target: "ペルソナを要約した想定読者1行"
last_update: YYYY-MM-DD
---
```

### Frontmatter の補足

- `title` と本文先頭の `#` 見出しは**意味を揃える**（完全一致でなくてよいが、検索意図は一致させる）
- `description` は **120〜160文字（Unicode・両端含む）**。正本レンジ。完了前に必ず実測する（「だいたい」不可）
  - **120未満 / 160超は未完了**（コミット・PR・week-queue `done` にしない）
  - 計測例（PowerShell）: `(Get-Content … -Raw | Select-String -Pattern 'description:\s*"(.*?)"' -AllMatches).Matches.Groups[1].Value.Length`  
    または Node: `node -e "const t=require('fs').readFileSync('PATH','utf8'); const m=t.match(/^description:\\s*\\\"([^\\\"]+)\\\"/m); console.log([...m[1]].length)"`
  - CTR meta（`rewrite_type=meta`）は title/H1/description が成果物本体。短い description はリライト不成立とみなす（手順: Vault `ctr-rewrite-queue`「meta 完了ゲート」）
- `tags` は 5〜10 個程度。記事テーマ・ツール名・シリーズ名を含める
- `site` は `toolarc.jp`（引用符の有無は既存記事に合わせてよい）
- `last_update` は更新したときだけ追記（任意）

## 収益導線（本文での書き方）

本文の信頼を損なう導線は入れない。案件キー・MD記法は [`affiliate-registry.md`](./affiliate-registry.md)、直リンク可否は `lib/affiliate/policy.ts`。

### CTA 配置（収益・CV記事）

第2〜3層の収益記事・本命CVでは、**同一の主目的／遷移先**を次の3点に置く（別商品の並列表記ではない）:

1. リード直後（今日の結論付近）
2. 本文中（比較表直後など）
3. まとめ前

- CV文言は**無料オファー型**を優先する。「詳細はこちら」のみにしない
- 本文の主力は**ボタン型テキストリンク**
- **バナーは記事末・サイド等の面のみ**（本文中盤へのバナー連打は禁止。比較記事**本文**へのバナー直貼り禁止。右レール共通枠は別チャネル）

Tips／チェックリストなど非収益型は、従来どおり**テーマに合う CTA を1本に絞る**（上記3点は収益記事向け）。

### アフィリエイト

- 比較・選定記事では **表** と「向く人 / 向かない人」をセットで書く
- リンクの前後に判断材料を置く（注意点、代替案、費用感、前提条件）
- 機能羅列ではなく、読者の課題解決に紐づけて訴求する
- 「絶対」「必ず」などの断定は禁止。条件・前提を明記する
- 直アフィ禁止の比較シリーズは、**本文**への `affiliate:` のみ禁止（周辺収益記事への弱リンク）。サイト共通の右レール枠・狭い幅横長枠（`RAIL_AFFILIATE_POOL` / `NARROW_AFFILIATE_POOL`・日替わり・同日は別案件）は比較Seriesでも可。本文禁止 ≠ レール／narrow禁止（`lib/affiliate/policy.ts`）

### 広告

- 記事品質・滞在価値・情報密度を優先する（広告収益のために本文を薄くしない）
- 過剰な挿入や本文の分断は避ける
- 広告は補助収益。まずは SEO と読者満足を満たす

### デジタル商品（note / 教材 / テンプレ）

- 記事内で先に無料価値を提供する（手順、チェックリスト、判断基準）
- **誰向けかが明確な CTA** を置く。非収益型・Tips は記事末に1つ（複数の別商品を並べない）。収益記事は上記「CTA 配置」の3点に同一オファーを置く
- 本文テーマと無関係な商品誘導はしない

## SEO

- **検索意図**: 初心者が今困っていること（How-to、チェックリスト、比較）
- **タイトル**: 主要キーワード + 読者メリット（煽り・過剰な記号は避ける）
- **description**: 誰向けか・何が分かるか・実測・差別化を1文に集約（**120〜160文字・実測必須**。Frontmatter補足）
- **本文**: キーワードの詰め込みより、見出しと表で意図を満たす
- **Hub 記事**: シリーズ全体の入口として、スポーク記事への内部リンクを入れる

## 禁止表現・注意

記事本文・記事案・構成案に共通する。

- 根拠のない「絶対」「必ず」「必ず成功」「公式保証」
- 未確認情報の断定、未確認の料金・制限・移行可否の断定（**執筆時点の日付**を本文または免責に書く。暦日は記事全体で少なくとも1回辿れれば足りる。詳細は「仕様・免責」の暦日の置き方）

## 仕様・免責（記事末尾）

StickyTOC は `##`（H2）のみ目次化する。免責を見出しにすると TOC ノイズになるため、**見出し化しない**。

### 本命形式（推奨）

まとめのあと `---` を置き、見出しなしの段落だけにする:

```md
---

本記事の内容は執筆時点（YYYY-MM-DD）の情報に基づきます。仕様は変更される可能性があります。重要な判断は公式ドキュメントで確認してください。
```

### 許容形式

注意を目立たせたいときのみ、引用＋太字ラベル（見出しではない）:

```md
> **免責**
> 本記事は執筆時点（YYYY-MM-DD）の…。仕様は変更され得ます。重要な判断は公式で確認してください。
```

### 禁止

- `## 免責` / `### 免責`
- `## まとめ・FAQ・免責` など、見出し文言に「免責」を含めること

### 含める内容

次のいずれかに近い形で締める:

- OpenAI / Anthropic / Cursor 等の仕様は変更されうる旨
- 記事は執筆時点（`date` / `last_update`）の情報に基づく旨
- 重要な判断は公式ドキュメントで確認する旨

### 暦日の置き方（必須／任意）

- **必須**: 暦日（`YYYY-MM-DD` または同等）が記事全体で**少なくとも1回**辿れること。免責の `執筆時点（YYYY-MM-DD）` で足りる（「本文または免責」の要件を満たす）
- **本文・今日の結論**: 範囲限定は「執筆時点」だけでよい。表の確認日・実測日など、読者価値がある暦日は置いてよい
- **任意（L1合否外）**: 同一暦日の連打（結論・各H2・つまずき・免責への複製）は薄くしてよい。必須修正にしない。適用は人間判断
